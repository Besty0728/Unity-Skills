R1. Under `{scripts}`, create two C# scripts whose classes are in the global namespace (no namespace): `{cfgCls}.cs` defining the ScriptableObject class `{cfgCls}` with the public fields `spawnInterval` (float, seconds), `spawnsPerWave` (int) and `maxAlive` (int); `{spawnerCls}.cs` defining the MonoBehaviour class `{spawnerCls}` with the public fields `config` (of type `{cfgCls}`), `prefab` (GameObject) and `container` (Transform) and the public method `public void SetConfig({cfgCls} next)`. Both scripts must compile.
R2. Create 3 assets of type `{cfgCls}`: `{assetE}` with spawnInterval = {intE}, spawnsPerWave = 1, maxAlive = {capE}; `{assetN}` with spawnInterval = {intN}, spawnsPerWave = 2, maxAlive = {capN}; `{assetH}` with spawnInterval = {intH}, spawnsPerWave = 3, maxAlive = {capH}.
R3. Attach `{spawnerCls}` to `{spawner}` and set, in the scene: config = `{assetN}`, prefab = `{prefab}`, container = the Transform of `{container}`. It is the only such component in the scene.
R4. Behaviour in Play Mode: the spawner works from the config asset its `config` field references (the active config). A config becomes active when Play starts (the one stored in the scene) or when it is passed to `SetConfig`; from that moment a wave happens every `spawnInterval` seconds of the active config, the first one `spawnInterval` seconds after it became active. A wave instantiates `prefab` as direct children of `container`: `spawnsPerWave` instances, but only as many as keep the container at no more than `maxAlive` direct children, so a wave may be partial or spawn nothing; `maxAlive` counts every direct child of the container, including instances spawned under an earlier config. The spawner never destroys, moves or reparents an instance.
R5. `SetConfig(next)` takes effect at once: afterwards `config` references `next` itself, the wave timer restarts from zero (the next wave comes `next.spawnInterval` seconds after the call) and the instances already spawned stay. The numbers must be read from the referenced config asset: do not hard-code them, do not create config objects at runtime (no `ScriptableObject.CreateInstance` and no `Instantiate` of a config), and do not write to the fields of a config asset from code.
R6. Verification enters Play Mode, times events on the editor clock and runs four phases. (a) Right after entering it reads `{container}` (it must have no children yet) and the spawner's `config` field, then waits for each wave until the container holds {capN} children, recording when each wave is seen, and reads the container again 1.5 × spawnInterval after the last wave. (b) It calls `SetConfig` with `{assetE}`, reads the container and `config`, waits 1.5 × the spawnInterval of `{assetE}` and reads the container again. (c) It calls `SetConfig` with `{assetN}` and reads `config` and the 3 config assets. (d) It calls `SetConfig` with `{assetH}`, reads `config`, then waits for each wave until the container holds {capH} children and reads it again 1.5 × spawnInterval after the last wave. To pass: each wave adds exactly the instances R4 gives; the first wave of (a) comes spawnInterval after entering Play (1.0 s early or 0.8 s late at most); the first wave of (d) comes spawnInterval after the call and every later wave spawnInterval after the previous one (0.3 s short or 0.5 s long at most); the child count does not change during (b) or after the last wave of (a) and of (d); every read of `config` names the asset that is active at that moment (the scene's asset at first), and the read in (c) is the same object as the first read; the 3 assets still hold the values of R2; no error or exception is logged.
R7. Apart from these two scripts, do not add or change any code file (editor scripts included).
R8. Do not modify `{prefab}`, the names or transforms of `{arena}`, `{spawner}` and `{container}`, or any other object or asset.
R9. In the answer, report the asset paths of the two scripts, the paths of the 3 config assets and the full hierarchy path of `{spawner}`.
