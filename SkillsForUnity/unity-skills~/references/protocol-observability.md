# Protocol: Observability

Four read-only endpoints close the loop after a mutation — most useful across Domain Reload, when the server briefly drops out (see "Target the right Editor" in the root `SKILL.md`).

## `GET /jobs/{id}?wait=<seconds>` — one request until the job settles

Script writes (`script_create`, `script_append`, `script_replace`, `script_rename`, `script_move`, `script_delete`) return `jobId` and `waitUrl` (`/jobs/<jobId>?wait=90`), and so does `asset_refresh` when its refresh starts a compilation (`compileTriggered:true`, e.g. after you wrote a `.cs` with your own file tools; its `resultData.compilation` is project-wide, `scope:"project"`). GET it and the server holds the request until the job is terminal or the wait runs out (capped at 120 s), then answers with the job snapshot: `status:"completed"`, or `"failed"` with the compile diagnostics in `resultData.compilation`; when the wait runs out first, `waitTimedOut:true` and a `hint` — GET the same URL again. The wait runs off the main thread (it only queues short status probes), so it never blocks Unity. If a domain reload starts meanwhile, it answers `503` (`COMPILING`, or `SERVER_STOPPED`) with `retryAfterSeconds`; the job survives the reload, so retry the same URL, as you would after a dropped connection. One command covers it all: `curl -s --retry 20 --retry-connrefused --retry-all-errors --retry-delay 2 "http://localhost:<port>/jobs/<jobId>?wait=90"` (use the port of the Editor that returned the job). Without `wait`, `GET /jobs/{id}` returns immediately; terminal snapshots include `resultData`, so ordinary polling preserves the same compilation and runtime evidence as long polling.

## `GET /compile/status` — did my script edit compile?

After `script_*` writes (or any change that recompiles) the editor runs a Domain Reload and the server briefly answers `503/504`. Once it responds again, this endpoint reports the last compilation without re-reading files: `{status, isCompiling, isUpdating, domainReloadPending, lastCompilation:{finishedAtUtc, durationMs, success, errorCount, warningCount, errors:[{file, line, column, message, assembly}], warnings:[...], truncated} | null}`. `errors` are capped at 200, `warnings` at 50. `lastCompilation` survives the reload (persisted via `SessionState` for the editor session), so the pass/fail verdict and exact error lines are still there after the server returns. For a single script write the `waitUrl` above is the shorter loop; use this endpoint for changes that recompile without a job (define or package edits, files written outside UnitySkills): wait out the transient unavailability → `GET /compile/status` for success + error lines.

## `GET /events` — long-poll event channel

Instead of hammering `/compile/status` in a loop, subscribe to a 500-entry in-memory ring buffer. Query: `since` (omit = wait only for events newer than the current max seq; `0` = replay the whole buffer), `timeout` (seconds, default 25, clamped 1–55), `types` (comma-separated filter). Response: `{status, events:[{seq, type, tsUtc, payload}], cursor, oldestSeq, dropped, timedOut}`; carry `cursor` into the next call's `since` to resume. Event types: `compilation_started` / `compilation_finished` (carries `firstErrors`, first 5) / `before_domain_reload` / `after_domain_reload` / `server_restored` / `playmode_changed` / `console_error` (throttled 20/s with `droppedSinceLast`) / `job_completed` / `job_failed`. `seq` is monotonic and never rewinds across reloads; a reload discards in-flight events, signalled by `dropped:true`. **Reconnect anchor:** the "compilation succeeded" event is lost when Domain Reload tears down the connection — after reconnecting, read `server_restored`, whose `payload` carries the `lastCompilation` summary, to recover the verdict you missed.

## `GET /analytics` — execution telemetry

Aggregates how skills have been performing. Query `?window=1h|24h|7d|all` (default `24h`) and optional `?agent=` to count only one client: canonical names such as `ClaudeCode` or `Codex` (`claude-code` is folded to `ClaudeCode`), or `(unknown)` for calls with no agent identity. When the filter is set, the response echoes it as `"agent"` next to `window`; without it the response has no `agent` field. Failed records in `recentErrors` may carry `err` (path-redacted message) and `target` (short argument summary). The same local data feeds `/skills/recommend`: at least 5 valid calls are required before a high failure rate applies a bounded 1–3 point penalty; slow skills are warned but not penalized. Client/permission errors are ignored, and telemetry disabled means recommendation order remains semantic-only. The answer is cached for 30 s, so count from the files below when you need exact, current numbers.

## `?diff=1` — what a write changed

Append `?diff=1` (or `true`) to `POST /skill/<name>` or `POST /skills/batch`. A successful response carries a top-level `sceneDiff` with `changed` / `added` / `removed`. A batch returns the net change across its successful steps, built after a transactional rollback. A read-only call returns a note instead, a dryRun captures nothing, and a failed diff degrades `sceneDiff` to an error object without touching the result. Any other value answers 400 `INVALID_MODE`. The write's own read-back (root doc, "Verify from the read-back") is usually enough; use the diff for broad or indirect edits.

## Change journal and log files

`editor_get_changes` reads a journal the plugin keeps in `Library/UnitySkills/`: the active `editor_changes.jsonl` plus rotated `editor_changes.1.jsonl` (newest) to `editor_changes.10.jsonl`, one JSON entry per line. The append that brings the active file to 2,000 entries or 8 MiB renames it to `.1` and shifts older files up; what falls past `.10` is dropped. Files are only appended to or renamed, never rewritten. If a rename fails (for example a reader holds the file open on Windows) the active file keeps growing and the next append retries; a gap left by a failed shift is closed first, so no file is lost early.

`seq` is monotonic across files and Domain Reloads (after a reload it continues from the newest file that has entries). The skill still answers from a 500-entry in-memory window (`retention`, `oldestSeq`, `dropped`); read the files for older history. Read them newest to oldest (active, `.1`, `.2`, …): a rotation during the read can only show you one file twice, never skip one. Ignore an unparseable last line of the active file, which is an append in progress, and de-duplicate by `seq`. Every `seq` between two cursors being present is the proof that nothing is missing.

Entry layout: `seq, type, source, agent, isPlaying, tsUtc, payload`. `agent` (REST caller id, `"mixed"`, `"unknown"`, or `null` for manual edits) and `isPlaying` are newer fields; entries written by older plugin versions lack them. The per-type additions are listed under `editor_get_changes` in the editor module doc.

The telemetry file (`Library/UnitySkillsTelemetry.jsonl`, rotated to `UnitySkillsTelemetry.1.jsonl` to `.3.jsonl` at 1 MB; one line per call: `ts, skill, agent, mode, ok, ms`, plus `errorCode`, `err` and `target` on failed calls only and `wfMs` (the workflow history bookkeeping time) on writes that recorded an undo task, with the project root shown as `<project>` and the home folder as `~`) and the audit log are written about 200 ms after a call so the client identity can resolve first. Both are also flushed straight away before a Domain Reload and when the Editor quits, so a record queued just before either survives.

## Compilation proof and recovery

`debug_force_recompile` returns an accepted compile job (`jobId`, `waitUrl`); request acceptance does not prove compilation. Its terminal `resultData.compilation` records `cycleId`, `startedAtUtcTicks`, `finishedAtUtc`, `assemblyCount`, `compiled`, `success`, `domainLoaded` and `domainLoadedAtUtcTicks`. Jobs bind to the fixed next compilation cycle after the request, rather than borrowing a recent successful result. The last 16 completed cycles are retained in `SessionState`, so a later empty or successful cycle cannot overwrite or substitute the requested cycle's evidence. A forced request fails at `no_compilation` when no matching assembly compilation occurs. A clean compilation remains at `reload_pending` until a later domain load proves that the compiled assemblies are available; elapsed time is insufficient proof. Unity may defer compilation at `waiting_play_mode_exit`; the job never exits Play Mode for the user. A refresh that needs no compilation may complete with `compiled:false`, which does not claim new types were loaded.

Pin all job reads with `?expectInstance=<original instanceId>` (also supported for `/logs`, `/progress` and `?wait=`). The Python client pins the identity from the accepted response and follows only that instance's registry port after a reload. Its polling budget uses a monotonic clock and retains the last job snapshot and phase if the connection drops before timeout. Recovery retries only job GETs; a write whose response was lost is not replayed. Domain reload still exposes temporary 503/504 or connection refusal.

All ordinary GETs, including `/health` and `/skills`, run through the Unity main-thread queue. Health reports `updateTickCount`, `playerFrameCount`, `playerFrameIdleMs`, and managed wake dispatch counters; successive responses show whether editor updates and player frames are advancing independently. It also names the plugin build that answers: `packageRoot`, the absolute folder Unity resolved `com.besty.unity-skills` to when this domain started serving, and `assembliesLoadedAtUtc`, when the running plugin assemblies were loaded (ISO-8601 UTC). Both change only on a domain reload, so after a manifest is repointed to another checkout they keep naming the old build until Unity has loaded the new one. A pending main-thread wake is not proof of an advanced frame. Background wake dispatch only posts to the captured synchronization context; Unity APIs execute on the main thread without changing focus. A blocked synchronous skill cannot be forcibly terminated safely; health/job requests may also time out while the main thread is blocked.
