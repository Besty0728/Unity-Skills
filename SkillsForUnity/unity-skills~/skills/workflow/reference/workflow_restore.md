### workflow_restore
Puts the scene and project assets back to a checkpoint. Only the caller's steps from that point on are reverted unless `agents` is `all`.

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| to | string | Yes | - | A `c<n>` id, an `s<n>` step, `last` (the caller's newest checkpoint) or a checkpoint label |
| agents | string | No | `self` | `self` or `all` |
| conflicts | string | No | null | Omit to refuse on conflicts (`WORKFLOW_CONFLICT` lists them), `"keep"` to skip them, or the conflict ids to overwrite |
| scope | string | No | null | Comma-separated targets to restore (see **Scope.**); omit for the whole restore |

**Returns:** `{ to, guard, restored, deleted, recreated, failed, skipped, coverage, undo, compileTriggered }`, plus `merged` when targets were merged property by property, `failedItems` (up to 20 `name (type): reason` strings) when something failed, and `skippedItems` (up to 20 `target (kept: <by> change <id>)` strings) when a kept conflict skipped work. `guard` is the checkpoint taken before the restore; `undo` is the call that reverts this restore (`workflow_restore {"to":"<guard>"}`). Ctrl+Z only reverts the scene, not the assets, so use this call to undo a restore. Script changes start a compile job (`jobId`, `waitUrl`). Play Mode returns `SEMANTIC_INVALID`; an unknown position returns `NOT_FOUND` with `recentCheckpoints`.

**Conflicts.** A restore refuses to overwrite changes made since the checkpoint that it did not make itself: a person's edit in the Inspector or the scene, or another agent's step on the same target. Such a refusal is `WORKFLOW_CONFLICT`, with top-level `conflicts` (each `{id, target, by, what, at}`, plus `confidence: "logged"` for journal entries) and `coverage` (`full`, `partial` when rotation dropped part of the journal, or `unknown`). Nothing changed and no guard was taken. Protocol: ask the user in one sentence, default to keeping their changes, then retry with `conflicts:"keep"` (every conflicting target is skipped and listed in `skippedItems`), or with the ids the user wants overwritten. A conflict that is not listed is kept. Targets are judged by their after-state: one still in the state the restored steps left is restored cleanly, one already at its before-state is skipped, and any other target is merged property by property. Properties only the restored steps changed go back; properties changed later, by another step or by hand, stay. A property changed by both is a leaf conflict: kept by default, listed in `conflicts` with an id that `conflicts:"keep"` or the id decides. Files with their own importer (textures, scripts, prefabs) are judged by their on-disk fingerprint, so an external edit to such a file is a conflict. A restore that removes an object it created treats a later change by someone else to any of its components or children as a conflict on that object; keeping it keeps the object. `conflicts` takes effect the same way for `workflow_undo_task`, `workflow_redo_task` and `workflow_session_undo`.

**Preview (dryRun).** `POST /skill/workflow_restore?mode=dryRun` applies nothing and returns the preview in `changes`: `to`, `label` (when `to` is a checkpoint), `agent`, `steps`, `plan` (`modify`, `delete`, `recreate`, `move`, `settings`, `merge`), `items` (up to 20 `name (type) action` strings, such as `Light (Light) merge (2 kept)`, or `... not written: scene is open, save it to apply`, then `moreItems`), `scope` (the normalized scope text), `danglingReferences` (`holder.propertyPath -> deleted object` strings, when the restore deletes an object that something else still references), `conflicts` (the same ids the refusal lists), `coverage`, `unresolvable` (`{target, reason}`, such as a scene that is not open) and `mayTriggerReload`. The preview is optional unless `dryRunPolicy` is on. `workflow_undo_task`, `workflow_redo_task` and `workflow_session_undo` preview the same way.

**Scope.** `scope` is comma-separated items: `entity:<id>` (a GameObject id also covers its components), an `Assets/` or `Packages/` path (trailing `/` = the folder and everything under it), an object name or hierarchy path (trailing `/` also covers children), or a setting key (trailing `.` = prefix). Example: `{"to":"c343","scope":"Player/,Assets/Art/"}`. An item that matches no target returns `SEMANTIC_INVALID` with a message starting `scope `, listing up to 10 targets; nothing changes. A scoped restore does not mark its steps `(undone)`.

**Open scene.** A `.unity` file of an open scene is not written: its objects are restored in memory, the scene is marked dirty, and `skippedItems` lists it with `scene is open`. Saving the scene applies the restore.
